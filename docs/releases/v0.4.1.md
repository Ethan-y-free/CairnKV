# CairnKV v0.4.1 — Benchmark Baseline & Raft Metrics

The first measured baseline. Single-node writes are fsync-bound; the cluster
exposes a per-proposal broadcast storm that collapses throughput at 8+ threads.

## Highlights

- Closed-loop benchmark client (`tools/cairnkv-bench`) with warmup/measurement
  barriers, p50–p999 latency, error classification, and before/after server snapshots.
- `scripts/bench.sh` runs the single/cluster matrix and archives raw JSON plus
  per-node logs under `docs/benchmarks/results/`.
- Per-second Raft metrics: proposals, fsync count/latency, apply count/latency,
  AppendEntries sends/responses/rejections, and per-peer `next`/`match`/queue depth.
- `docs/benchmarks/v0.4-baseline.md` records the measured data and the bottleneck analysis.

## Correctness

- Heartbeat ping-pong is gone: an empty AppendEntries response no longer triggers
  another AppendEntries when the follower is already caught up.
- `LogStore::Append` now checks `ftruncate` when rolling back a partial record.

## Validation

- Build: 54/54 (Debug and Release).
- `ctest`: 7/7.
- Cluster smoke: election, kill leader, re-election, committed data retained, follower redirect.
- Partition smoke: isolated leader rejects linearizable reads, majority partition serves, rejoin converges.
- Baseline (2 vCPU AMD Ryzen 9 8945HX VM, ext4, RocksDB 8.9.1):
  - single-node Put: 1176 / 1532 / 1796 ops/s at 1 / 8 / 32 threads;
    `sync_calls : proposals` = 1:1, mean fsync 500 µs.
  - cluster Put: 513 ops/s at 1 thread; 8 / 32 threads collapse to 114 / 125 ops/s
    with 0 errors, traced to ~100× redundant AppendEntries and a lossy bounded send queue.
  - reads: single-node linearizable/stale Get ≈ 16.9k / 16.5k ops/s;
    cluster linearizable 7.4k, stale 15.8k ops/s.

## Known limits

- This is a baseline checkpoint; group commit and pipelined replication land in W4-2.
- Three nodes and the client share a 2 vCPU VM, so cluster high-thread numbers are pessimistic.
- Stale reads still traverse the Raft core queue.
