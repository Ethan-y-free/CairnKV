# CairnKV v1.0.0 — API Freeze

v1.0 marks the point where `libcairnkv`, the wire protocol, and the operational
contract stop moving, so downstream services can pin a fixed tag and build
against it.

## Highlights

- Public SDK frozen: Put / Get (linearizable + stale) / Scan / Delete / Status,
  with leader redirect handled by the client.
- Single Raft group with election, log replication, ReadIndex reads, WAL group
  commit, and per-peer replication pipelining (4 in-flight batches).
- Operational surface: `cairnkd`, `cairnctl` (including partition/unpartition),
  `cairnkv-bench`, per-second Raft metrics.
- README rewritten as a v1.0 project overview: positioning, architecture and
  threading model, failure semantics, validation matrix, quick start, SDK
  example, and a docs index.
- Documentation set: README, DESIGN-draft-v2, W4/W5 case studies, benchmark
  methodology, and release notes.

This is a milestone, not a feature drop: **no wire-protocol or Raft behavior
changes relative to v0.4.2**. Data directories are compatible.

## Correctness

- term/vote persisted before any RequestVote reply.
- AppendEntries validates `prevLogIndex/prevLogTerm`, truncates conflicting
  suffixes, and only acknowledges after WAL fsync.
- commit rule: current-term entry with majority `match_index` and a durable
  local WAL.
- ReadIndex: current-term no-op must be committed before serving linearizable
  reads; an isolated old leader times out instead of serving stale data.
- `stale` reads return `applied_index` and never claim linearizability.

## Validation

- Build: 56/56 (Debug, `Linux-GCC-Debug`; v0.4.2 code plus the version bump
  and documentation).
- `ctest`: 7/7.
- `cluster-smoke.sh`: leader kill, re-election, data preserved.
- `partition-smoke.sh`: minority cannot commit, isolated leader rejects
  linearizable reads, stale read returns the local value, rejoin converges.
- Performance reference (v0.4.2, original 2 vCPU VM): cluster Put
  8t/32t = 1894/1901 ops/s, p99 6.5/20.9 ms; single-node Put
  8t/32t = 3574/3475 ops/s.

> Absolute benchmark numbers depend on the host and disk state. A later VM
> state measured ~1120 µs fsync (vs ~500 µs at v0.4.2), cutting single-node
> Put to ~1130 ops/s. Always compare with a same-session A/B run; see
> `docs/case-study-w5.md`.

## Not shipped

- **Follower asynchronous group-commit acknowledgments** (W5-1): implemented,
  unit-tested, and smoke-tested, but same-machine A/B showed -10%/-15% cluster
  write throughput on the current VM. The pipeline cannot be filled under
  closed-loop load with ~1.1 ms fsync, so the extra scheduling hops dominated.
  The patch is archived outside the repo; revisit on faster storage or with
  open-loop load.
- **Snapshot / InstallSnapshot**: remains the designated stretch item and is
  deferred to post-v1.0. The design format (magic + version + index/term + KV
  set + CRC) is reserved in DESIGN-draft-v2 §5.6.

## Known limits

- Single Raft group; no sharding / multi-Raft.
- WAL is not compacted; a long-running node grows its log indefinitely.
- No lease read / follower read; linearizable reads pay a heartbeat round.
- No dynamic membership, TLS, or multi-machine deployment tooling.

## Upgrade

- From v0.4.x: stop the node, replace the binary, restart. The on-disk WAL,
  hard state, and RocksDB state are unchanged.
- From v0.2/v0.3: use the v0.4.2 upgrade path first; this release does not
  change the format.
