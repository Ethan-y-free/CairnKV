# CairnKV v0.4 性能基线（W4）

本文件记录 W4 优化前的基线数据，用于和 WAL 组提交、复制流水线优化做前后对比。

## 方法

- **客户端模型**：closed-loop。每个压测线程持有一个阻塞 `Client`，同一时刻只有一个在途请求，因此并发度等于线程数。
- **计时点**：请求发出前、收到完整响应后各取一次 `steady_clock`，只统计成功请求的延迟；超时与错误单独计数，不混入分位。
- **预热**：默认 2s，预热请求不计入结果；测量窗口默认 10s。
- **读 workload**：测量前先用单线程写入 `keyspace` 个键，避免把 NotFound 当作成功。
- **服务端快照**：测量前后各取一次 `status`，用 `commit_index` / `last_applied` / `wal_bytes` 的差值核对客户端看到的吞吐。
- **已知偏差**：closed-loop 存在 coordinated omission，服务端卡顿时客户端会自动少发，p99 偏乐观。本基线用于前后对比；开环定速模式属于后续工作。

## 环境

- 构建：`Release`（`-O2`，GCC 13.3.0）
- 虚拟化：VMware（`ethany-VMware-Virtual-Platform`）
- CPU：2 vCPU（AMD Ryzen 9 8945HX）
- 内核：7.0.0-42-generic
- RocksDB：8.9.1
- 文件系统：ext4（`/dev/sda2`，`/tmp` 非 tmpfs）
- 拓扑：单节点；3 节点本地集群（127.0.0.1:6666–6668）
- value 大小：64B
- keyspace：1000

## 分析

### 单节点：fsync 串行是唯一瓶颈

- 每秒 `sync_calls` ≈ `proposals`（1:1，约 1830 次/秒），`sync_avg_us` ≈ 500 µs；core 线程约 91% 的时间阻塞在 `fdatasync` 上。
- Put 吞吐 1t → 8t → 32t 仅从 1176 涨到 1532/1796 ops/s，p50 从 834 µs 膨胀到 5.4/17.7 ms：增加并发只增加排队，不提高 fsync 合并率。
- 1 线程理论上限 1/500µs = 2000 ops/s，实测 1176，差值来自 RPC 往返、apply（17 µs）与调度。
- linearizable Get 与 stale Get 几乎相同（16.9k vs 16.5k ops/s）：两者都进入 Raft core 队列，stale 读没有旁路 core。

### 集群：低并发合理，高并发 Put 异常塌陷

- Put 1 线程 513 ops/s：leader fsync（~500 µs）+ follower fsync（~650 µs）+ RTT，约为单节点的 44%，符合预期。
- **Put 8/32 线程反而降到 114/125 ops/s，p99 达 132/452 ms**，且超时/错误为 0——请求都在排队，不是失败。
- 机制初判：
  1. 每条 proposal 都 `BroadcastAppendEntries()`；
  2. `SendAppendEntries` 每次从 `next_index` 重发最多 64 条，而 `next_index` 只在成功响应后推进；
  3. 每个 peer 的 `PeerClient` 一次只发一条、等响应；队列上限 256，满时 `pop_front` 静默丢弃最老消息。

  高并发下三者叠加：proposal 产生速度超过单 peer 串行复制能力 → 队列溢出丢消息 → 重复发送同一批 → follower 日志显示 `append_req` 约 5000–8700/s 而 `appended` 常为 0 → commit 推进被拖慢，形成正反馈式退化。
- 读路径未受影响：stale Get 15.8k ops/s（与单节点持平），linearizable Get 7.4k ops/s（ReadIndex 多数派往返）。说明网络与 leader core 未被阻塞，瓶颈在复制/提交路径。

### 测量环境限制

- VM 只有 2 vCPU，3 个服务端进程与压测客户端共享同一台机器：8/32 线程时 CPU 争用会放大延迟，集群 Put 的数字偏悲观。
- 但广播风暴的证据来自 leader 自身计数器（每秒发送量是有效 proposal 的约 100 倍），与 CPU 争用无关；W4-2 优化后应在同一环境下复测。

### 下一步优化目标

1. **WAL 组提交**：`fdatasync` 移出 core 线程、按批合并（单节点 Put 目标 > 5k ops/s）；
2. **复制流水线**：每 peer 允许 W 个 in-flight 批次，发送/接收解耦，按 peer 状态补窗，去掉"每条 proposal 全量广播"；
3. 队列满时回退 `next_index` 并显式重试，禁止静默丢消息；
4. stale 读旁路 core（后续）。
